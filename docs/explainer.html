Jitterbug · how it works and how we built it

Jitterbug, explained

Jitterbug makes fake phone calls to a voice AI agent over a deliberately bad network. Then it checks three things: did the agent hear the caller, did it get the job done, and if not, was that the network's fault or the AI's?

Each strip of little squares on this page is 20 milliseconds of a voice call. Green squares arrived, red ones were lost on the way, and amber ones arrived too late to be played.

The core idea, live

What packet loss does to a sentence

On a call, your voice is cut into 20 ms packets and sent over the internet. Move the sliders to damage the network and see which words of the caller's sentence the agent never receives. This uses the same formulas as network.py.

Share of packets the network drops.
1 = losses spread out. Higher = losses come in clumps, like Wi-Fi or 4G.

This is the project's main finding in miniature. Word error rate can stay low while the one word that matters, like "four" or the caller's name, disappears, and the booking fails.

In the order it happened

How we built it, step by step

Each step solved one problem and was tested before the next one started. The red notes are real bugs we hit along the way. They make good interview stories.

  1. Set up a Python project

    pyproject.tomlsrc/jitterbug/.gitignore

    We used uv, a fast Python package manager, to install Python 3.12 and make a virtual environment (.venv), a private folder of libraries just for this project. pyproject.toml lists the libraries. Heavy speech models are an optional "extra", so tests never need them.

    uv python install 3.12
uv venv --python 3.12
uv sync --extra models     # numpy, fastapi, faster-whisper, onnxruntime...

  2. Fake a bad network

    network.pytests/test_network.py
    • Audio is a list of numbers (16,000 per second). We cut it into 20 ms packets of 320 numbers each, like a real call.
    • Packet loss uses the Gilbert-Elliott model. The network flips between a Good state and a Bad state, so losses come in bursts.
    • Jitter gives every packet a random delay. The jitter buffer waits a set time, and late packets are dropped.
    • Concealment fills a gap by repeating the last good packet at half volume, then silence. G.711 squeezes audio like an old phone line.
    # average burst B, loss rate L  →  r = 1/B,  p = L·r / (1−L)
r = 1.0 / burst_len                  # chance of leaving the Bad state
p = loss * r / (1.0 - loss)          # chance of entering it
bad = rng.random() < loss
for i in range(n):
    lost[i] = bad
    bad = draws[i] >= r if bad else draws[i] < p
    BugThe first jitter buffer was a fixed 60 ms, so a "3% loss" Wi-Fi profile actually lost 12%. Real receivers (WebRTC's NetEQ) size the buffer to the jitter, so we made it adaptive: 3 × jitter + 20 ms.

  3. Score what the agent heard

    scoring/wer.pyscoring/quality.py
    • WER (word error rate) = wrong + missing + extra words, divided by the words actually said. Before comparing, we normalise text so "4 p.m." equals "four pm".
    • DNSMOS is a small Microsoft model that predicts a 1–5 "how good does this sound" score from the audio alone, with no clean copy needed.
    BugWhisper wrote "7pm" (no space) and "830 PM" (no colon), and the booking logic missed the time. The text normaliser now splits digits from letters and reads 830 pm as 8:30 pm.

  4. Build an agent to test

    speech.pyagent.pyscenarios/*.yaml

    A voice agent is a loop: speech-to-text → brain → text-to-speech. We used local Whisper as the ears and macOS voices as the mouth. The brain is a simple restaurant-booking assistant that collects party size, time and name. We used rules instead of an LLM on purpose: the brain always answers the same way, so if a call fails it's because of what the agent heard.

    def handle(self, audio):
    heard = self.stt.transcribe(audio)       # ears
    reply = self.brain.reply(heard)          # brain
    reply_audio, first_ms = self._speak(reply)  # mouth, sentence by sentence
    return AgentTurn(heard, reply, reply_audio, timings)
    BugThe "Aman" macOS voice spoke gibberish at the start of sentences, even on a perfect network. We were measuring a broken voice, not the network, so we switched to "Rishi".
    BugThe first call took 17 seconds because Whisper was loading. We added a warm-up so loading time isn't counted as latency.

  5. Run calls and decide who's to blame

    runner.pydiagnosis.py

    The runner plays the conversation turn by turn and records everything. The diagnosis compares each call with the same call on a clean network:

    if call.task_success and fast_enough:      verdict = "pass"
elif call.task_success:                    verdict = "latency"   # right but slow
elif baseline_also_failed:                 verdict = "agent"     # fails even on clean
elif some_turn_was_misheard:               verdict = "network"   # names the lost words

    Latency = 300 ms waiting for the caller to finish + network delay + speech-to-text + brain + time until the first sentence of the reply is spoken.

  6. Make it a backend service

    api/main.pyapi/db.pyapi/jobs.pyapi/schemas.py
    • FastAPI gives the web endpoints. Pydantic checks every request, so bad input gets a clear 422 error.
    • SQLAlchemy stores runs and calls in SQLite, and the same code works on PostgreSQL.
    • A run can take minutes, so the API answers at once with 202 Accepted and a run id. A background worker does the calls and saves each one as it finishes.
    @app.post("/runs", status_code=202)
def create_run(body: RunCreate, request: Request, session: DB):
    run = Run(id=uuid.uuid4().hex[:12], scenario=..., status="queued")
    session.add(run); session.commit()
    request.app.state.jobs.submit(run.id, scenario, profiles, body.seeds)
    return run                      # client polls GET /runs/{id}

  7. Add a command line and charts

    cli.pyreport.py

    jitterbug sweep runs one scenario under many network conditions, prints a table, saves results.json, and draws the packet-loss chart that's in the README.

  8. Write tests and switch on CI

    tests/tests/fakes.py.github/workflows/ci.yml

    Real speech models are slow and huge, so tests use fake engines. Each word becomes a short beep, and the fake "ears" drop any word whose beep the network destroyed. So tests still fail for the right reason (lost audio means lost words), and all 65 run in a few seconds. GitHub Actions runs them on every push.

    BugSaving results overwrote each call's network settings with just the profile's name. A test now checks that the full settings survive.

  9. Plug into Pipecat

    integrations/pipecat.pytests/test_pipecat.pytests/test_stream.py

    Pipecat is a popular open-source framework for voice agents. A Pipecat bot is a pipeline of processors passing frames (chunks of audio, text, signals) along. We added:

    • A drop-in network processor anyone can put into their own Pipecat bot to hear how it copes with a bad network.
    • An adapter that runs a real Pipecat pipeline for each test call and watches every frame with an observer to collect transcript, reply, audio and timings.
    async def process_frame(self, frame, direction):
    await super().process_frame(frame, direction)
    if isinstance(frame, InputAudioRawFrame):   # the user's voice
        self._impair(frame, "uplink")            # damage it in place
    await self.push_frame(frame, direction)      # pass everything on
    BugTwo-sentence replies got cut after the first sentence. The Mac voice needs about 0.7 s per sentence, but Pipecat was told a reply is over after 0.2 s of quiet. Now the adapter waits for the "LLM response ended" signal, which Pipecat sends only after all of the reply's audio.
Hands on

Run and test it yourself

Open Terminal and start in the project folder. Each command is safe to run as often as you like.

Go to the project

cd ~/Desktop/jitterbug

Run all 72 tests (about 7 seconds, every one should pass)

uv run pytest

Test calls under 6 network conditions (about 50 seconds)

uv run jitterbug sweep restaurant_booking

Same, with the bot running as a Pipecat pipeline

uv run jitterbug sweep restaurant_booking --agent pipecat

Packet-loss sweep with a chart (0–20% loss, 3 calls each, about 3 minutes; the chart lands in runs/)

uv run jitterbug sweep restaurant_booking --preset loss_sweep --seeds 3

Keep the audio so you can listen to what the agent heard on each turn

uv run jitterbug sweep restaurant_booking --save-audio

The clickable front end. Start the API, then open http://127.0.0.1:8000/docs in your browser. FastAPI builds this page automatically. Click POST /runs → Try it out, paste the example below, press Execute, then use GET /runs/{run_id} with the id you get back.

uv run jitterbug serve
{"scenario": "restaurant_booking", "profiles": ["phone_line", "mobile_4g_weak"], "seeds": 2}

To read a failed call, open the newest runs/…/results.json and look for "diagnosis". It says in plain words which turn failed and what was lost.

Glossary

Words you'll hear

Packet
A small chunk of call audio sent over the internet. Here, 20 ms each.
Packet loss
Packets that never arrive. Bursty loss (several in a row) hurts more than the same amount spread out.
Jitter
Packets arriving at uneven times. The receiver's jitter buffer waits a little to smooth it out, and drops packets that are too late.
Concealment
Patching a gap so it doesn't click, for example by repeating the last good sound quietly.
G.711 / mu-law
The classic phone-line codec: 8,000 samples per second, 8 bits each.
STT / TTS
Speech-to-text (the agent's ears) and text-to-speech (its mouth).
Whisper
OpenAI's speech-to-text model. We run it locally with faster-whisper.
WER
Word error rate: the share of words heard wrongly. 0% is perfect.
MOS / DNSMOS
Mean Opinion Score, 1 (bad) to 5 (excellent). DNSMOS predicts it from audio alone.
Latency
How long after the caller stops talking the agent starts replying. About 2 s and above feels broken.
Endpointing / VAD
Deciding the caller has finished speaking (voice activity detection).
Baseline
The same call on a perfect network, used to tell network faults from agent faults.
Seed
A starting number for the randomness, so the same settings always drop the same packets.
Pipecat frame
One message in a Pipecat pipeline: a bit of audio, some text, or a signal like "user stopped speaking".
202 Accepted
The HTTP answer for "got it, working on it in the background".
CI
Continuous integration: GitHub runs the tests automatically on every push.
Learn it by doing

Build it yourself, step by step

The best way to own this project is to rebuild the core in a fresh folder, writing each piece yourself and comparing with the real code only when you're stuck. Each milestone is small and ends with a check.

Milestone 1 · 1 hour

Packets

Load a WAV file with soundfile, cut it into 320-sample packets, and drop 10% at random. Save and listen.

Done when you can hear the gaps.

Milestone 2 · 2 hours

Bursts and jitter

Replace random loss with Gilbert-Elliott, then add jitter and a buffer. Write one pytest that checks the loss rate.

Done when 10% loss measures 10% ± 1.

Milestone 3 · 1 hour

Ears and scores

Transcribe clean and damaged audio with faster-whisper, then compute WER with jiwer.

Done when WER rises as loss rises.

Milestone 4 · 2 hours

A 3-turn call

Write the booking brain and a loop that plays three caller lines and checks the final booking.

Done when a clean call passes and a 30% loss call fails.

Milestone 5 · 2 hours

An API

Wrap it in FastAPI: POST /runs starts a run in the background and GET /runs/{id} shows results.

Done when you can start a run from /docs.

Milestone 6 · 2 hours

Pipecat

Write a FrameProcessor that drops packets from InputAudioRawFrames, and test it with Pipecat's run_test.

Done when the test shows damaged frames.
